## 一、高危（建议尽快修）

### H1. 存储层元数据全无并发保护 —— 日志修了锁，数据没修

**位置**：`zhishiku/kb/store.py`（alloc_id / _save_index / create_entry / move_zone）、`auth.py`（_save）、`reqsys.py`（add_application / resolve_application）

**问题**：
- 上一轮修复给 `audit.py` 的 logstate 加了跨进程锁，但**同样模式（读-改-写 JSON 文件）的 counters.json、index.json、keys.json、applications.json 全部无锁**——既没有进程内锁，也没有跨进程锁。
- FastAPI 的同步 `def` 端点运行在**线程池**里并发执行；说明书又明确支持"服务运行时同时用管理菜单"（跨进程）。两个并发 `create_entry` 会读同一个计数器值 → **分配出相同标记 ID**，后写覆盖先写，索引只剩一条，另一条孤儿文件留在磁盘。
- AI 连续提交两条 REQ（`alloc_req_id`）同理可撞号；`move_zone`（写新文件→删旧文件→改索引三步）与并发的 `get_entry` 交错时会返回 None 或旧分区。

**方案**：仿照 audit.py 的做法，加一个全局 `store_lock`（进程内 threading.Lock + 复用 `logs/.xlock` 的 msvcrt 跨进程锁），把 `alloc_id / alloc_req_id / create_entry / update_entry / delete_entry / move_zone / rollback / _save(keys) / applications 写操作` 全部置于锁内。改动集中、可一次完成。

### H2. 请求体 1MB 上限可被 chunked 编码绕过（对外开启 = 远程内存 DoS）

**位置**：`zhishiku/kb/main.py` 中间件第 1 步

**问题**：上限判断只读 `Content-Length` 头。HTTP 允许 `Transfer-Encoding: chunked` 不带此头，此时 `cl = 0` 直接放行；FastAPI 的 `body: dict` 会把整个请求体读进内存再解析。对外访问开启后，任何人可以无限制地 POST 超大 body 把服务内存打爆。

**方案**：中间件里对无 Content-Length 的非 GET 请求改用流式读取并累计字节数超限即 413；或更简单——无 Content-Length 的 POST/PUT 一律要求 `Transfer-Encoding` 白名单校验，并在路由层改用 `request.stream()` 截断读取。

### H3. 匿名用户可永久破坏哈希链校验（审计 DoS / 日志注入）

**位置**：`zhishiku/kb/public_api.py` `/api/apply` + `audit.py` 的写日志格式

**问题**：`self_name` 只截断 20 字符、**不过滤换行符**，随后被写进 access.log 的 `who` 字段。攻击者（对外开启后匿名即可）提交 `self_name = "x\n伪造行内容"`，日志文件里就多出一条物理行。`audit.verify()` 逐行校验哈希链，注入的行没有合法哈希 → **校验永远报"断裂"**，且断裂位置之后的真实日志也无法自证清白。等于匿名者一键废掉你的防篡改审计。

**方案**：所有进日志的外部可控字段（`self_name`、`reason`、申请 ids、entry title 等）在 `_log()` 入口统一做 `\n`/`\r` → 空格 的清洗（在 audit 层做一次，所有调用方受益）。

## 二、中危

### M1. 申请状态机无守卫：已执行的 REQ 可被覆盖成"已拒绝"

**位置**：`admin_api.py` `reject_req`、`reqsys.resolve_req / resolve_application`

**问题**：`resolve_req` 不检查当前状态，网页端 `reject_req` 也不像 `exec_req` 那样校验"待审核"。后果：一条已执行的申请可被事后改成"已拒绝"——**审计记录与知识库实际状态矛盾**（经验已追加，申请却显示被拒绝）。已批准的访问申请同理可被再拒绝覆盖。

**方案**：`resolve_req/resolve_application` 内建状态守卫：`status != "待审核"` 时拒绝变更（CLI 已查，把它下沉到 reqsys 层双保险）。

### M2. AI 会话状态非原子写：崩溃瞬间丢光全部提醒

**位置**：`AI/brain/state.py` `save()`

**问题**：知识库侧有 `atomic_write_text`（临时文件+os.replace），brain 侧却是 `SESSION_FILE.write_text` 直接覆写。写盘中途断电/强杀 → JSON 截断 → 下次 `load()` 捕获 ValueError 后**静默冷启动**：所有未触发提醒、事件、权重、统计全部归零，且无任何提示。对"提醒"这种核心能力这是数据丢失级事故。

**方案**：`save()` 改用与 zhishiku 相同的原子写模式（可抽一个公共小函数，或直接复制 5 行）。同理 `stats.py` 的 weights_logstate、`ruleload.py` 的计数文件、`refine.py` 的队列文件都是直接覆写，建议一并原子化。

### M3. 历史备份文件名只有秒级精度：同一秒两次修改 = 丢一份备份

**位置**：`store.py` `_backup()`

**问题**：备份文件名 `now()` 精确到秒。脚本化/批量操作（或管理员手快）一秒内两次修改同一知识 → 第二次 `shutil.copy2` **覆盖**第一份备份，"可回滚到任意历史版本"的承诺出现缺口。

**方案**：文件名追加毫秒（`%Y-%m-%d_%H-%M-%S-%f`），或同名时加 `_2` 后缀。

### M4. 临时授权 hours 无边界 + int() 未捕获

**位置**：`admin_api.py /api/keys/temp`、`auth.temp_grant`

**问题**：`int(body.get("hours", 24))` 传入 "abc" 抛 ValueError → 未捕获 → 500；传 0/负数生成"出生即过期"的授权；传 999999 等于永久授权，违背"临时"语义。

**方案**：钳制 `1 <= hours <= 720`（30 天），非法值返回 400。

### M5. 训练层会稀释"安全告警"注意力权重

**位置**：`AI/brain/train.py` `maybe_train`

**问题**：规则是"频率低于均值 ×0.8 → 权重 -0.02"。安全告警在日常生活中命中极少，freq≈0 恒低于均值 → 每 10 轮降一档，直到贴住种子值 -20%（2.0 → 1.6）的地板。设计意图是"安全永远最高优先"，但机制让它随常态对话**持续向下漂**；闲聊即使降权也只降到 0.48，两者差距被系统性压缩。

**方案**：安全告警类型加入"永不降权"白名单（只许升不许降），或至少排除出自动训练集合。一行 `if t == "安全告警": continue` 即可。

### M6. 推演层同值结论的置信永不升级

**位置**：`AI/brain/reason.py` `forward()` 开头

**问题**：`if then_var in self.facts and 值相同: continue`——已存在的结论即使新路径置信更高也不更新。例：先由低置信规则推出 `X=高（0.3）`，之后强证据路径（0.9）被跳过，最终报告里 X 的置信永远停留在最早的低值，误导裁决。

**方案**：值相同但新置信更高时更新 Fact 并留痕（ trace 记一条"置信升级"）。

## 四、设计层面的观察（非缺陷，供拍板）

1. **授权是永久的、条目级的**（除临时授权）：访问方一旦获准 P1，知识内容更新后他仍看最新版。若将来有"按版本快照授权"的诉求，现在 ID 不回收的设计是兼容的，但需要在授权记录里加版本字段。
2. **规则晋升依据 = AI 自报的对账计数**（rule_reconcile.json）：管理员终审兜底，设计成立；但建议晋升 REQ 的 proof 里附上计数文件哈希，防"AI 状态文件被手改后骗晋升"。
3. **哈希链防的是"不懂 logstate 的篡改者"**：能写 logs/ 的人可重算整条链。作为本地单机工具这已够用；若哪天对外多人共用，需要考虑把链头定期外发（如邮件/另一台机器）锚定。
4. **AI 密钥明文落盘**（`AI/state/ai_key.txt`）：本机场景合理；建议补一句"该文件勿同步进网盘/git"，并把 `.gitignore` 建议写进说明书（修复报告已提，未并入主文档）。
5. 变更 #6 诚实清单里的遗留（原子操作清单、多假设并行、预测持久化→自动验证触发器、规则适用边界检查）依然成立，其中**"预测持久化→自动验证"**是推演闭环最关键缺口：目前对账全靠人手动调 `reconcile()`，建议优先做——提醒事件到期时自动生成"该验证哪些预测"的待办即可用小成本闭环。
